# Participant diagnostics and rehearsal testing

## Participant Activity

Open **Teams & Accounts → Participant activity** as a dashboard owner on the server. This is a separate contest-local event store, not the administrator audit trail. The header shows an unresolved-incident badge; opening it selects this screen. Timeline filters include team, time window, severity, category and source. Pages contain up to 200 events. CSV downloads contain up to 10,000 newest matching events and escape spreadsheet formula prefixes. Incidents can be acknowledged or resolved; a new occurrence reopens a resolved incident. These actions are themselves audited.

The participant gateway records sign-in/sign-out outcomes, submission requests, clarification requests, API/resource requests, HTTP status, latency, request IDs and bounded metadata. A successful submission request means the API received it; the final verdict is a separate native PC² observation. Resource entries mean a request occurred, not proof that a participant read a PDF. The gateway never writes request bodies, source contents, passwords, cookies or raw session tokens to the event log. The proxy overwrites the peer header so LAN clients cannot choose the recorded IP through that header.

The participant browser module records route changes, recognized UI actions, form-submission events without field values, source-file count/size/type without names or contents, interface error class/script basename/line, request status/latency, WebSocket state, network reports and page lifecycle. It never records keystrokes, arbitrary console/error text, full URLs, screenshot/video, other websites, or other programs on a laptop. Browser reports can be incomplete or manipulated; they are labeled as browser reports and are never used for authentication, grading or a cheating verdict.

Native PC² submissions, verdict changes, clarifications and native client connection changes are observed read-only every five seconds while the dashboard process runs and an event is active. The observer uses the existing administrator bridge, not another account/client. Initial records are explicitly labeled imported history and use observation time; it does not invent an original wall-clock timestamp. Intermediate native transitions while the dashboard is stopped may not be reconstructible. The gateway continues collecting requests independently while the dashboard is closed.

Browser signals are sent about every 10 seconds. After 45 seconds without a signal, an inferred incident says **No recent browser signal**. A suspended/closed tab can cause the same observation as a network outage; this is not proof of disconnection. A received normal page close or successful logout suppresses the gap check. A new signal automatically resolves a gap incident. Wrong Answer and other contest verdicts do not create a system incident. Actual browser errors and server failures do, with browser/client evidence distinguished from server confirmation.

Existing WTI sessions are not forcibly logged out. New successful sign-ins bind a hashed token to its server-verified team identity. Pre-existing sessions are validated by WTI but may not have an authoritative identity mapping until their next sign-in. A team name reported by such a browser remains visibly unverified. Events from a previous signed-in team are not transferred to a newly signed-in team by the browser queue.

The browser script starts on the next page load/refresh. It retries bounded batches after connectivity returns; at most 100 events are queued in a tab. A closed/crashed browser or prolonged offline period can lose unsent events. The endpoint accepts bounded structured batches only, validates same-origin requests and participant sessions, and throttles traffic. No collection system can report an unreachable laptop's error immediately while it is offline.

## Storage and recovery

Each contest owns `participant-activity/activity.sqlite3` and a private signing key under a 0700 directory, with private files. Events use a serialized HMAC-SHA256 chain. Verify it through **Verify log integrity**. Retention is 30 days or 200,000 events, checked in batches of 500 writes. Pruning retains a chain anchor. The diagnostic presence table is capped at 2,000 entries and incident records at 10,000; timeline data remains subject to its own limit. The activity database contains token hashes only in its private identity/presence tables; those are excluded from API views and cleared in full-backup copies. Full backups use SQLite's backup API and preserve the retained activity chain/key. Separate new contests do not inherit old diagnostic events.

A privileged attacker with access to both the database and signing key can replace history; local HMAC is not an external immutable audit service. Logging/storage failures do not deliberately reject otherwise valid contest requests. The gateway emits a bounded service warning and diagnostics UI failures remain visible. Its private operational log is available under **System → Service logs → gateway**.

## Participant Test

Open **System → Participant test**. **Open participant app** launches the real participant application at the managed LAN URL, with no administrator access in that page. Use a private browser window and a participant account for independent browser storage. Testing from the server verifies the application/proxy path; testing another physical laptop is still required to verify Wi-Fi connectivity, client firewall/routing and that device's browser.

**Prepare rehearsal & download access** requires owner reauthentication and typed confirmation. It creates an independent draft with all problem definitions/private judge data, resource copies and one fresh participant account. Currently published resources may be published in that rehearsal explicitly through the checkbox; other copies remain drafts. It returns private CSV credentials. It copies no old teams, runs, clarifications or results and never changes the selected/active contest or starts clocks. Review and switch through Contests yourself; only one contest may be active.

The readiness table shows configured tests/statements, not fabricated successful scenario checks. Test accepted/incorrect solutions and compile/runtime failures yourself in the rehearsal's participant app, then inspect Submissions and Participant Activity. It uses the actual client/server/judge path. No current student submission is automatically executed or rejudged by this feature.

## Expected and actual output

Submission details show **Expected output · Reference answer** and **Actual output · Saved program output**. The input/expected answer comes from current private judge data; saved reports may belong to an earlier data revision/judgement. The installed PC² retained-output format does not reliably identify a test number for every stdout file. Such outputs are visibly labeled by report and are not claimed to belong to the selected test. Missing output remains unavailable, empty output remains empty, and compile failure explicitly states that the program did not run. No diagnostic view reruns source to manufacture missing output.

Compile/runtime failures have red report badges and red stream headers, with nonempty relevant failure streams expanded. Classification also checks saved verdicts and nonzero exit codes: some wrapper failures retain false PC² stage-failure flags. Successful, empty and unavailable streams remain distinct. Compiler warnings/messages alone are not labeled compile failure. If PC² retained only its nonzero-exit diagnostic note, the actual-output panel explicitly says that program output is unavailable and identifies the note separately.

## Deployment and tests

`lcpc/infra/deploy_activity.py --state /absolute/managed/instance` stages the updated gateway on the other managed loopback port (8090/8092), validates Caddy configuration, checks readiness, gracefully reloads the same Caddy file, checks the public config route, and drains the retired gateway before cleanup. It preserves the LAN origin/CIDR/Origin guard and never routes the organizer dashboard. It requires a Caddy version with documented SIGUSR1 configuration reload support; see [Caddy command-line signals](https://caddyserver.com/docs/command-line#signals). It does not restart PC², WTI or the isolated judge, or change contest time/results. The managed gateway port is remembered for later starts.

Isolated tests:

```sh
python3 -B lcpc/admin/tests/test_participant_activity.py
python3 -B lcpc/admin/tests/test_participant_routes.py
node --test lcpc/branding/tests/activity.test.cjs
node --test lcpc/admin/tests/run-details.test.cjs
```

These use temporary stores/fake backends. They cover trusted versus reported identity, data minimization, session transitions, native history/verdict observation, missing-signal recovery, incident recurrence, chain tampering/concurrency/pruning, gateway compatibility/policy, roles/CSRF/workspace isolation, CSV and rehearsal preparation without any live clock switch or student-code execution.

## Connection monitor, inline filters and dashboard identity

**Teams & Accounts → Team connections** lists every contest team, native PC² login state, browser signal state, IPs, last signal, missing duration and verified observed intervals. Teams must refresh their participant app once to load the current collector. Existing sessions may remain reported/unverified until their next successful sign-in; no sign-out is forced. Historical network membership is not invented.

The collector sends heartbeats about every ten seconds. After 45 seconds without a signal the server observer checks for a gap every five seconds; the open dashboard polls its incremental connection alert feed every five seconds. Explicit page departure is debounced for eight seconds to avoid normal refresh alerts. Another recent tab for the same team and IP suppresses a device-loss incident; normal logout is distinct. These are observations of browser reachability, not proof of Wi-Fi exit, router leases or an SSID. Background suspension and a stopped dashboard observer can delay detection. On-screen alerts and the incident ledger work without desktop permission. Use **Enable desktop alerts** to grant browser notification permission; delivery requires an open dashboard and the browser/OS permitting notifications. Old retained incidents are not replayed as new desktop notifications on opening the dashboard.

`connection_periods` retains at most 50,000 signal intervals within the 30-day retention window. Verified totals merge overlapping tabs and exclude gaps, stopping at the last received heartbeat. Unverified observations are shown separately. The LAN CIDR is recorded per interval; changing address/network creates a new interval. No response packet or heartbeat can describe what happened on an unreachable laptop immediately. The encrypted full backup retains this history along with the event chain; diagnostic authentication mappings/presence are cleared in the backup copy.

Event timeline rows open details by pointer or Enter/Space; selecting text and nested action buttons remain independent. Search and filters live inside the timeline panel with a bounded, separately scrolling table. Connection and rehearsal lists have their own local search/status controls. Native account permissions are individual checkboxes with an internal search and exact selected-count display. Filtering never modifies the selection; new account defaults come from PC²'s own permission groups. Saving an empty selection really requests no permissions. Protected service-account rules, owner reauthentication and native confirmation remain enforced.

**System → Participant test & access** and the Overview access card show only the active workspace's assigned managed LAN address. Detected private interfaces are read on the server; an obsolete or offline workspace address is not advertised as a usable team URL. Login, Instructions, authenticated Problem PDFs and Scoreboard links have Copy actions. The address refreshes every fifteen seconds in the center. **Run server checks** verifies the managed HTTP routes, private-PDF sign-in gate, active judge-data configuration and native automatic-judge login state; it never submits or executes student code. The manual rehearsal checklist records your observations per problem and scenario. Configuration changes invalidate its saved revision. These checks cannot certify a different laptop's network path or replace actual participant rehearsal submissions.

**System → Dashboard identity** customizes the sidebar name/subtitle, primary button color, sidebar color, active-section background/indicator, menu and row hover colors, keyboard focus outline and a private PNG/JPEG logo. Semantic success/error/warning/destructive colors remain fixed. Preview does not save. Owner-only writes use existing same-origin/CSRF protection and an optimistic version check. Raster uploads are bounded to 1 MiB and 2048 pixels per side; SVG/remote URLs are not accepted. Logo data and preferences live in the central control database and its encrypted backup. This changes only organizer pages, including organizer sign-in, and never edits participant logos/styles/instructions. Browser-notification permission is an organizer choice and is not changed by branding. Fixed dashboard roles remain distinct from PC²'s detailed permission checkboxes.
